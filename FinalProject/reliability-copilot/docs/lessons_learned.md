# Lessons Learned — Wilson Neira

This project taught me that building a distributed system is very different from only describing one. Early on, I had a clear high-level idea for Reliability Copilot, but the first version was still too simple. It could classify a failure event locally, but it did not yet have the worker path, queue-style processing, or enough system behavior to support the final experiments. What went wrong at that stage was that the project idea was ahead of the actual implementation. Next time, I would move faster from the architecture idea into a small but realistic end-to-end pipeline earlier.

One of the biggest lessons for me was about observability. At first, it was easy to talk about observability in the report, but much harder to build the project in a way that actually exposed meaningful system behavior. Once I started structuring the project around experiments, I realized that observability is what turns a system into something understandable. Without measurements like latency, throughput, and behavior under injected failures, the system is just code running. With those measurements, it becomes something I can reason about and improve.

I also learned that AI alone does not make a strong systems project. The most useful part of this project is not just labeling failures, but designing the surrounding system so that the AI or lightweight inference path does not become a single point of failure. That connects directly to course concepts around fault tolerance, graceful degradation, and performance tradeoffs. I now understand more clearly that the hard part is not just making a model say something useful, but making the overall system stay responsive and measurable when demand rises or components slow down.

The most challenging bug or design issue for me was moving from a synchronous local classifier toward a queue-backed background workflow that could support the final experiments. That shift forced me to think more concretely about bottlenecks, worker throughput, and fallback behavior. In a local prototype, it is easy to hide those problems. In a more realistic design, they become visible very quickly. That really reinforced course ideas about distributed systems not being just about functionality, but about how systems behave under load and failure.

If I were doing this again, I would start with a smaller final architecture from the beginning instead of starting with a very simple local version and then stretching it later. I would also collect experiment-ready metrics earlier so that the reporting stage would be smoother. Still, I think this project shows real growth from day one of the course to the end. I moved from mostly thinking about whether something works to thinking much more carefully about tradeoffs, measurements, reliability, and stakeholder value.
